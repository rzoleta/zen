01 / Assessment

A working foundation with uneven boundaries

I would keep the stack and refactor in place. Zen is a local vocabulary app with six screen implementations. Its complexity comes from coordinating persistence, time, gestures, and native UI, not from its size.

Keep

Several choices are already good

  • Strict TypeScript, a pinned pnpm version, a lockfile, and passing local checks.
  • Pure queue and FSRS functions accept an explicit time. Session tests cover early retries, undo, dismissals, and preserving the visible card.
  • SQLite stores durable progress; Zustand holds the current session. That division fits the product.
  • Reusable text, button, card, screen, select, segmented control, and furigana components already exist.
  • The custom query listener batches row changes and tears down its native listener when unused. The iOS word menu has an explicit platform implementation.
  • The content extractor checks fields, counts, media sizes, and records its source archive hash.
Refactor

The costly parts cross too many boundaries

  • The review screen coordinates reads, preloading, commands, session timing, errors, navigation, toasts, and haptics.
  • scheduler/index.ts combines scheduling policy, SQL queries, grading transactions, reset commands, and word reads.
  • UI types come from hooks; settings defaults come from the seed module; the database module imports UI.
  • Settings repeat complete controls despite having a local SettingRow helper.
  • Home and direct review entry assemble queues through different data paths. Progress repeatedly processes complete review history.
  • The test suite does not establish that on-device database commands or native review interactions work end to end.

Recommendation: approve a staged internal refactor. Treat data corrections and changes to failure behavior as separate decisions. Passing tests support the existing core; they do not yet establish release readiness.

These are intended defaults for the planned v5 client. Missing/collected cache entries still load on demand. Explicit invalidation refreshes active reads. Use finite garbage collection for unused details; measure deck/cache memory before tuning it. Do not use staleTime: "static", which blocks invalidation.

TanStack documents always mode for reads that require no network and the distinction between staleTime, refetch triggers, and garbage collection. Retry and focus defaults are deliberately explicit so adoption does not silently change existing failure or refresh behavior.

Grade with cache synchronization

  1. Animation completes → guarded mutation → grade command

    Capture ID, answer time, and duration once. No optimistic cache or queue change; no automatic mutation retry.

  2. SQLite transaction commits → return saved card

    Database failure keeps the visible-card retry path and leaves cache/session untouched.

  3. Prevent older reads winning → publish committed detail → invalidate dependent families

    Cancel or supersede affected in-flight reads before writing cache values. Update only the card fields in the joined detail so word content is retained. Use one shared invalidation map.

  4. finishCard → render next detail from shared cache

    An immediate retry of the same ID must receive the saved snapshot. Background metric refreshes do not reorder the active session.

  5. Handle refresh failure separately from commit failure

    Once SQLite commits, a refetch error must not report the grade as unsaved or offer a path that records it again. If detail-cache synchronization fails, re-read the saved row without resubmitting the grade.

Replace one read system with one cache

During the incremental read migration, retain a temporary adapter from the existing batched SQLite table events to query invalidation so old write paths still refresh new query consumers. While this adapter owns invalidation, mutation bindings must not also trigger duplicate refetches. Card writes must invalidate review history too, preserving the current reset/truncate workaround.

After every runtime write uses a centralized command and its cache effects are tested, switch to command-owned invalidation and remove the transition adapter, old subscriptions, custom useLiveQuery, and unused change-listener configuration. Bootstrap writes finish before any query mounts. Do not leave two competing invalidation systems in the final structure.

Query functions can call promise-based local reads. Query function contract. The named key families and command effects above are specific to Zen; TanStack supplies invalidation and prefetching, but does not infer which SQLite tables a query depends on.

Why this amount of structure: each layer corresponds to responsibilities already present in the code. Keep the pnpm workspace and SQLite. There is no second runtime consumer that warrants extracting a shared package, and introducing Postgres would change the local-only product.
